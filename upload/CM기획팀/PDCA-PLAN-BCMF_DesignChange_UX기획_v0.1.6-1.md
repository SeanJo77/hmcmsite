# BCMF 설계변경 웹프로그램 사용자 경험 기획 v0.1.6-1

> **요약**: 설계변경 건을 중심으로 현재 처리단계, 자료 흐름, 업로드 자료 분류를 한 화면에서 이어 보게 하는 기획이다.
>
> **작성일**: 2026-06-19

---

## 1. 기획 목적

CITIS 자료는 게시글과 첨부파일 중심으로 쌓인다. 그래서 설계변경 한 건의 원인, 검토자료, 회신, 승인요청, 현재 상태를 한 번에 파악하기 어렵다.

BCMF 설계변경 웹프로그램은 파일함이 아니라 **설계변경 한 건의 진행 흐름을 보는 업무 화면**이어야 한다.

---

## 2. 실사용자

| 사용자 | 주 사용 상황 | 필요한 정보 |
|--------|--------------|-------------|
| 시공자 | 실정보고, 설계변경 요청, 보완자료 제출 | 제출해야 할 자료, 보완요청 내용, 최신 제출자료 |
| 공사감독원 | 제출자료 검토, 보완요청, 검토의견 정리 | 변경 사유, 근거자료, 도면/수량/내역, 이전 회신 |
| 사업단 | 승인요청, 결과등록, 전체 현황 관리 | 승인 대상, 보완 중인 건, 금액 영향, 공구별 진행 현황 |
| 설계사/기술검토자 | 기술검토, 도면/수량/내역 확인 | 검토요청 배경, 관련 첨부자료, 최신 설계자료 |

---

## 3. 실제 자료 흐름에서 확인한 문제

근거 자료는 다음 폴더의 정리 흐름을 기준으로 본다.

`03_설계변경_과정추적_사례`

이 폴더에는 대호지교, 천의1터널, 역천교 관련 자료가 설계변경 과정 추적용으로 모여 있다. 여기서 확인되는 공통점은 다음과 같다.

| 확인한 흐름 | 기획에 반영할 점 |
|-------------|------------------|
| 대호지교는 사전검토, 회신, 수량자료, 승인요청, 공사비 검토가 여러 날짜에 걸쳐 이어진다. | 한 건의 자료를 날짜순 타임라인으로 봐야 한다. |
| 천의1터널은 록볼트, 패턴, 시공방법, 설계도서 수정처럼 표현이 달라도 같은 시설 관련 자료가 이어진다. | 제목뿐 아니라 공구, 시설명, 자료 성격으로 묶어야 한다. |
| 역천교는 기초형식, 철근 겹이음, 가시설, 가교 등 여러 이슈가 섞인다. | 같은 시설 안에서도 세부 변경 이슈를 구분할 수 있어야 한다. |
| 검토, 회신, 실정보고, 승인요청, 설계도서 폴더는 문서 성격 기준이다. | 폴더명을 업무 처리단계로 그대로 쓰면 안 된다. |
| 공문, 검토서, 도면, 수량표, 공사비 파일이 한 묶음으로 올라온다. | 업로드 시 자동분류와 예외 수정 방식이 필요하다. |

대호지교 예시 흐름은 다음과 같다.

| 날짜 | 자료 흐름 |
|------|-----------|
| 2025-07-22 | 상부공 시공방안 변경 사전검토 보고 |
| 2025-08-12~2025-08-18 | 사전검토 요청, 통보, 관련 공문 |
| 2025-11-11 | 지반조사 수량 변경 자료 |
| 2025-11-18~2025-12-08 | 설계변경자료 송부, 승인요청 공문 |
| 2026-06-12 | 축도폭 조정에 따른 공사비 검토 |

따라서 화면은 “승인요청 폴더”나 “설계도서 폴더”를 따로 보는 방식보다, **대호지교라는 건을 선택한 뒤 날짜순 자료 흐름을 보는 방식**이 맞다.

## 4. 반영 방향

| 방향 | 이유 |
|------|------|
| 설계변경 건을 중심으로 둔다. | 시공자, 공사감독원, 사업단은 파일 하나가 아니라 한 건의 진행 과정을 봐야 한다. |
| 처리단계 1~8단계는 업무 진행 상태로 둔다. | 자료 보관 폴더가 아니라 현재 업무 위치를 보여주는 기준이다. |
| CITIS 자료는 날짜순 타임라인으로 둔다. | 요청, 검토, 회신, 승인 흐름은 시간 순서로 봐야 이해된다. |
| 자료 성격 태그와 관련 처리단계 태그를 분리한다. | 하나의 자료가 검토자료이면서 승인요청 근거가 될 수 있다. |
| 폴더 업로드는 기본값 적용 후 예외만 수정한다. | 현장 자료는 여러 파일이 한꺼번에 올라오므로 파일별 수동 입력은 부담이 크다. |

## 5. 화면 구성

| 화면 | 역할 |
|------|------|
| 전체 목록 | 설계변경 건을 상태, 공구, 시설, 자료 성격으로 찾는다. |
| 건 상세 | 변경 사유, 현재 처리단계, 다음 업무, 금액 영향을 본다. |
| 자료 타임라인 | CITIS 게시글과 첨부자료를 날짜순으로 본다. |
| 자료 업로드 | 폴더/압축파일을 올리고 자동분류 결과를 확인한다. |
| 단계 처리 | 검토완료, 보완요청, 미승인, 승인요청, 공문등록을 처리한다. |
| 이력/출력 | 처리 이력과 보고용 요약을 확인한다. |

## 6. 처리단계

| 단계 | 이름 |
|------|------|
| 1 | 실정보고 접수 |
| 2 | 실정보고 검토 |
| 3 | 실정보고 승인요청 |
| 4 | 실정보고 결과등록 |
| 5 | 설계변경 접수 |
| 6 | 설계변경 검토 |
| 7 | 설계변경 승인요청 |
| 8 | 설계변경 완료 |

처리단계는 자료 폴더가 아니다. 현재 업무가 어디까지 왔는지 보여주는 상태값이다.

---

## 7. 업로드 방식

폴더를 올릴 때는 먼저 묶음 유형을 선택한다.

- 실정보고 제출 묶음
- 사전검토/기술검토 묶음
- 설계변경 승인요청 묶음
- 설계도서/내역/수량 묶음
- 결과통보/회신 묶음
- 섞여 있음

파일명으로 1차 자동분류하고, 시공자 또는 공사감독원은 `확인필요`, `미분류`, `중복의심`, `새 차수`만 수정한다.

---

## 8. 기획 원칙

1. 기본 단위는 파일이 아니라 `설계변경 건`이다.
2. 처리단계는 자료 폴더가 아니라 업무 진행 상태다.
3. 자료는 날짜순 타임라인으로 쌓는다.
4. 자료는 하나의 성격만 가진다고 보지 않는다.
5. 업로드는 파일별 수동 입력보다 자동분류 후 예외 수정 방식으로 간다.
6. 보고용 내용은 목록, 상세, 타임라인, 이력에서 자연스럽게 이어져야 한다.
